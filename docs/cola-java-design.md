## 研究与技术适配

已做的只读初查固定到 `alibaba/COLA` commit `352e1a867538d9cd40e1b11e4028fa652fc97557`。当时来源工作区干净，HEAD 没有直接 tag；尚未验证远端发布状态，不能称为“官方最新发布版”。完整研究尚待实现阶段完成。

后续研究按资料索引、规则交叉核验、完整写读链路三个层次推进：

1. 复核来源与目标仓库状态，区分来源提交和本地改动；沿用可追溯的研究基线。
2. 以标准 Web 多模块模板确定架构形态，结合 README、模板 POM、样例和必要组件源码核对职责、命名和依赖。编译依赖与运行时调用分别画清，避免混用 Web 模板与 craftsman 的整套模块图。
3. 至少追踪一条写入链路和一条查询链路，覆盖入口、对外契约、Application、Domain、Gateway、基础设施、数据访问、对象转换、异常、事务和测试。
4. 记录关键来源相对路径、类或章节、固定提交及文档代码差异。区分 COLA 规则、项目约定、技术适配和建议实践；示例写法只有在适用范围核实后才能推广为规则。
5. 核验许可证与归属要求；复用上游片段时保留必要声明。

初查发现标准 Web 模板仍使用 Java 8 / Boot 2.7.2，craftsman 使用 Java 8 / Boot 2.7.5，而仓库其他部分采用更新技术版本。最终示例需独立适配 Java 21 / Boot 3，不能直接复制旧构建配置。

实现阶段根据官方资料与实际编译确定具体 Boot 3.x、COLA 组件、Lombok、MapStruct 和 processor 版本，并记录它们；这些是待核验的技术事实，尚未在访谈中指定版本号。遵循 Boot 的依赖管理，按具体 API 迁移 Jakarta 包，保留目标项目已核验兼容的既有技术选择。

## Skill 内容与流程

优先使用现有 `skill-creator`，核验 Codex 当前支持的 Skill 格式。主 `SKILL.md` 保留触发范围、核心约束、开发流程、参考入口和完成标准；详细规则与长示例按任务分支下沉到相对链接指向的资源。

必须覆盖的内容包括：

- 架构与命名：模块和包职责、允许及禁止的依赖、API 与 Application 实现、Command/Query 执行逻辑、Entity/Value Object/Gateway、DTO/DO、转换类、Controller、数据访问接口的落位，并配正确示例和违规反例。
- 技术适配：Java 21 / Boot 3 的构建、依赖、Jakarta API 和测试配置；不强制额外 COLA 组件、preview 特性或无关技术设施。
- 工具库：优先标准库和已有依赖；Lombok 不破坏封装，MapStruct 只做结构映射，通用工具类不承载业务逻辑。其他库按实际需要选择。
- REST 与 HTTP：资源建模、方法语义、安全性与幂等性、路径和查询参数、分页排序过滤、状态码、业务错误码、业务行为、无状态与适用缓存语义。区分 HTTP 标准、REST 架构约束和项目命名约定。
- Controller 路由：完整应用内业务路径写在方法级映射，保留已确认的统一前缀；路径体现真实业务模块、小写与 kebab-case，集合用复数资源名。类型、父类或接口不提供隐式业务路径前缀。
- 类规模与职责：按下一节落实，核心上限与例外须在 `SKILL.md` 可见。
- 来源、审查清单、行为验收用例及安装说明，明确每项检查的覆盖范围。

开发流程需形成可执行顺序：检查项目约定和版本 → 明确用例与修改范围 → 确定层、对象、名称和依赖 → 预判类职责与规模 → 实现业务和边界 → 完成接口及转换 → 补充适当测试 → 格式化、编译、测试和审查 → 汇总结果及未解决项。

交付的 Skill 应能直接回答“这段逻辑放哪里、叫什么、依赖谁、谁来调用”，并让实际任务按条件读取相关参考资料。`agents/openai.yaml` 按核验后的实际规范和需要添加；不为目录外观创建空资源。

## 完整示例与工具

### 销售订单

最小教学模型包含 `CREATED` 和 `CANCELLED`：至少一条明细，数量和单价为正，金额由明细计算。这些约束只服务于本示例，不推导成真实订单系统的通用要求。

示例应展示创建、查询和取消的完整链路，包含领域规则、边界接口、基础设施实现、对象转换与测试。请求入口与应用接口采用所选标准多模块方案；纯查询和需要领域行为的调用按 ADR 0002 分别落位。内存数据的生命周期和线程安全边界要写清。

Q9 已确定在完整示例中实际组合使用 Lombok 和 MapStruct：前者用于合适的数据对象，后者承担结构转换，领域对象保留受控构造与行为。通过 Java 21 编译、processor 生成结果及映射测试核验联合配置和数据正确性。

测试应覆盖领域不变量、应用协作、真实 HTTP 契约、错误及响应序列化、查询路径、取消重试与并发下的一致性。首次取消时间由服务端生成，相同业务输入重试保持原记录；错误路径不改变已存状态。创建接口不会仅因取消接口采用 PUT 而自动获得幂等保证。

### Java 文件行数工具

Q10 已确定交付轻量统计工具及验证。它发现候选问题，职责归类和例外判定由 Codex 完成；不演化为通用静态分析平台。

- 按项目格式化后的 Java 源文件物理总行数统计，包含 package、import、注解、空行、注释、内部类、嵌套类和辅助类型。500 行允许，501 行进入超限候选。
- 输出实际检查范围、路径、物理行数及候选结果。默认用于本次新增或修改文件，不能由局部结果宣称全仓合规。
- 生成文件依据明确生成来源或构建产物目录排除；名称、后缀或随意注释不足以证明生成来源或例外资格。
- 用独立临时夹具验证 500/501 行、文件末尾有无换行、常见换行形式、内部类型计数和生成文件排除，验证后清理。正常示例保持自然规模。

业务逻辑类超限须按业务能力、用例或协作边界拆分，保持领域封装、事务边界和行为；未超限但职责混杂也须识别。声明型或数据型类可在职责单一、超长来自声明且可维护时保留，包含复杂行为的 Entity 仍按业务逻辑类判断。

新增业务类满足上限，修改不得让原本合规的业务类超限。局部修复存量超长类时，在授权范围内合理处理；超出范围的重构记录原因与后续建议，不把遗留问题标记为合规。每个超限文件报告路径、行数、职责判断，以及“已拆分／符合声明或数据例外及依据／存量未处理及原因”。
